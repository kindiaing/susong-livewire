# 差异 / 损耗 / 退货 — 全链路实现方案探讨

> 状态：草案，待进一步探讨  
> 日期：2026-08-22  
> 关联模块：采购、库存、拣货、配送、签收、损耗单、售后退货

---

## 一、概念定义

| 概念 | 含义 | 典型发生环节 | 数量方向 |
|------|------|-------------|---------|
| **差异（Discrepancy）** | 应拣/应送数量与实际数量不一致 | 拣货、配送签收 | 可多可少 |
| **损耗（Loss）** | 商品在库内或流转中发生的损失/报废 | 库存盘点、拣货、配送 | 只减不增 |
| **退货（Return）** | 已交付商品退回 | 采购退货（供应商）、售后退货（商户） | 退回入库 |

三者的核心区别：
- **差异** = 数量不一致，需要判定责任方和处理方式
- **损耗** = 确认丢失/损坏，需要扣减库存并记录原因
- **退货** = 商品物理退回，需要入库 + 退款

## 二、当前系统现状

### 2.1 全链路状态流

```
采购入库 → 库存 → 拣货(待分配→拣货中→已完成) → 配送(待配送→配送中→已完成) → 签收
```

### 2.2 各环节已有的差异/损耗相关设计

| 环节 | 已有机制 | 缺失部分 |
|------|---------|---------|
| 采购入库 | `PurchaseOrder` 有 `total_amount` / `actual_amount`，`PurchaseItem` 有 `status` | 入库时无"实收数量"录入，采购差异无法自动识别 |
| 采购退货 | `PurchaseReturn` 完整状态流（待审核→已审核→已出库→完成） | 仅处理已入库后的退货，不处理入库时的数量差异 |
| 库存 | `InventoryService` 有 `stockIn` / `stockOut`，`InventoryLog` 记录流水 | 无盘点差异处理，无自动损耗触发 |
| 拣货 | `PickingTaskItem` 有 `required_quantity` / `picked_quantity`，状态含 `STATUS_DISCREPANCY` | 差异仅标记，无后续处理流程；差异部分商品在库存中"虚存" |
| 配送 | `DeliveryTask` 有状态流，`DeliveryTaskSequence` 有顺序和签收 | 签收时无实收数量录入，配送差异无记录 |
| 签收 | `Order.status` 记录签收状态（STATUS_SIGNED=4） | 无实收/应收对比，签收差异无载体 |
| 损耗单 | `LossOrder` 完整状态流（待审核→已通过→已执行→已关闭） | 目前仅手工创建，无自动触发机制 |
| 售后退货 | `OrderReturn` 完整状态流（待审核→已审核→已退货→退款完成） | 功能较完整 |
| 差异记录 | `Discrepancy` 模型存在（状态 1-5） | 用途和触发机制不明确，未与各环节打通 |

## 三、逐环节方案分析

### 3.1 采购环节

#### 场景
供应商发货 100 箱苹果，实际到货 95 箱（少发 5 箱）或到货 102 箱（多发 2 箱）。

#### 现有问题
采购入库时录入的是采购明细数量，没有"实收数量"字段，系统无法自动识别差异。

#### 方案选项

**方案 A：采购明细增加实收数量字段**
- `PurchaseItem` 增加 `received_quantity` 字段
- 入库时录入实收数量，系统自动计算差异
- 差异处理：
  - 少收：差异记录到 `Discrepancy`，可选择"补发"或"扣减采购单金额"
  - 多收：可选择"退回"或"增加采购数量"
- 优点：差异在最源头被发现
- 缺点：入库操作多一步

**方案 B：入库时直接走采购退货**
- 入库时发现差异，直接创建 `PurchaseReturn`
- 优点：复用现有流程
- 缺点：语义不清（退货 vs 到货差异）

### 3.2 拣货环节

#### 场景
系统要求拣 50 斤苹果，实际只拣到 45 斤（库存实际不足或商品损坏）。

#### 现有问题
- `PickingTaskItem` 标记了 `STATUS_DISCREPANCY`，但差异无后续处理
- 按 `picked_quantity` 出库后，差额 5 斤在库存中"虚存"（系统有但实际没有）
- 没有人对差异负责，也没有审批流程

#### 方案选项

**方案 A：差异直接少发，自动生成损耗单**
- 拣货完成时，差异自动触发创建 `LossOrder`（损耗单）
- 损耗单走审批流程（待审核→已通过→已执行→已关闭）
- 审核通过后扣减库存差额
- 订单按实际拣货数量配送
- 优点：流程清晰，损耗有审批
- 缺点：拣货完成不能直接完成，需等损耗单审核

**方案 B：差异先标记，拣货完成后统一处理**
- 拣货时只记录差异，不阻断流程
- 拣货任务完成后，管理员在差异列表中统一处理
- 可选择：生成损耗单 / 补拣 / 忽略
- 优点：不阻断拣货流程
- 缺点：差异处理滞后，库存虚存时间较长

**方案 C：差异直接扣减库存（无审批）**
- 拣货完成时，按 `picked_quantity` 出库
- 差额部分直接走 `InventoryService.stockOut` 记录为"拣货损耗"
- 不生成损耗单，仅记录日志
- 优点：简单直接
- 缺点：无审批，损耗无人负责

### 3.3 配送环节

#### 场景
配送 50 斤到商户，商户签收时只收到 48 斤（运输损耗/丢失/少送）。

#### 现有问题
- 签收时无实收数量录入
- 配送差异无记录载体
- 差异金额结算无机制

#### 方案选项

**方案 A：签收时录入实收数量，差异自动处理**
- 签收操作增加"实收数量"录入
- 差异自动：
  - 生成配送差异记录（`Discrepancy`）
  - 差异金额从订单中扣减（商户少付）
  - 差异部分生成损耗单（公司承担损失）
- 优点：商户端体验好，差异即时处理
- 缺点：签收操作复杂化

**方案 B：签收后走售后退货流程**
- 签收按全量签收
- 如有差异，商户事后发起 `OrderReturn`（售后退货）
- 优点：复用现有流程
- 缺点：时效性差，商户需主动发起

### 3.4 签收后的损耗

#### 场景
生鲜在配送过程中变质，商户拒收部分商品。

#### 关键问题
- 这算配送差异还是损耗？
- 拒收的商品是否需要物理退回？
- 退款金额如何计算？

#### 分析
- 如果在签收时发现 → 配送差异（方案 3.3-A）
- 如果签收后才发现 → 售后退货（方案 3.3-B）
- 拒收商品不退回（生鲜变质无价值），但需要损耗记录

## 四、损耗单（LossOrder）定位

### 当前状态
`LossOrder` 有完整状态流：待审核(1) → 已通过(2) → 已执行(3) → 已关闭(4)，支持作废(9)。

### 可选定位

**定位 A：全环节统一损耗出口**
- 采购差异、拣货差异、配送差异、库存盘点损耗 → 全部生成 `LossOrder`
- 不同来源用 `source_type` 区分（purchase / picking / delivery / inventory）
- 优点：统一管理，审批流程一致
- 缺点：LossOrder 职责膨胀

**定位 B：仅用于库存盘点和手动损耗**
- 自动差异走 `Discrepancy` 模型
- `LossOrder` 仅用于定期盘点和手动报损
- 优点：职责单一
- 缺点：两套差异处理流程，维护成本高

**定位 C：LossOrder + Discrepancy 分层**
- `Discrepancy` 记录原始差异（各环节自动触发）
- 需要扣减库存的差异，由 `Discrepancy` 触发生成 `LossOrder`
- `LossOrder` 负责审批和库存扣减
- 优点：职责清晰，Discrepancy 是记录层，LossOrder 是处理层
- 缺点：两层模型，流程较长

## 六、全链路差异/损耗流向图（草）

```
采购入库
  ├─ 实收 < 应收 → Discrepancy(purchase) → 补发 or 扣款
  └─ 实收 > 应收 → 退回 or 增加采购

拣货
  ├─ 拣货 < 需求 → Discrepancy(picking) → LossOrder → 审批 → 扣减库存
  └─ 拣货 > 需求 → 多余退库（较少见）

配送签收
  ├─ 实收 < 应送 → Discrepancy(delivery) → LossOrder → 审批 → 扣减库存 + 退款商户
  └─ 实收 > 应送 → 多余退回（较少见）

库存盘点
  └─ 账实不符 → LossOrder(inventory) → 审批 → 调整库存
```
